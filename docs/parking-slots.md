# 停車格偵測：為什麼實車一直是 0 格

從 v0.3.x 起，停車格在實車上一直回報 0 格。這份文件記錄最後是怎麼找到原因的，
以及 v0.4.5 改了什麼。方法本身見 `ParkingSlotDetector.kt` 的開頭註解。

## 先確定線有沒有被找到

拿使用者車機存下來的原始四分割畫面（`raw_20261103_181414`，地下停車場，自己停在格子裡），
走一次 `tools/parking_proto.py`，先把抽出來的線全部印出來：

```
   0 ( -1.52, -2.71)→(  4.40, -2.90) 長 5.92m 角  91.9°     ← 車尾那條橫線
   1 ( -1.25,  3.44)→( -1.24, -2.40) 長 5.84m 角 179.9°     ← 格子左邊的長邊
   2 (  1.18, -2.32)→(  1.27,  3.52) 長 5.84m 角   0.8°     ← 格子右邊的長邊
  18 ( -1.36,  3.28)→(  2.24,  3.49) 長 3.60m 角  86.6°     ← 車頭那條橫線
```

**四條邊全部都抽到了。** 所以問題不在影像、不在校正、也不在線段抽取，
而在後面「把線湊成格子」的那一段。接下來就是逐關往下追是哪一關把它刷掉。

## 三個獨立的原因，缺一不可

### 1. 無限長直線的假交叉，把格子從中間切兩半

`_pair` 找出長邊對（線 1、線 2，間距 2.47 m、重疊 5.74 m，全部過關）後，
會去找橫過這一對的線。`intersect()` 算的是**無限長直線**的交點 ——
於是線 13（(−3.43,−2.30)→(−2.82,−1.53)，只有 0.98 m，而且整條都在格子外兩公尺處）
延伸過來也算出了一個交點，落在格子正中間。

格子是由**相鄰兩個**交叉切出來的，所以：

| 交叉配對 | 結果 |
|---|---|
| 線 18 ↔ 線 13 | 一邊只有 0.17 m → 丟掉 |
| 線 13 ↔ 線 0 | 兩個交叉方向差 52° → 丟掉 |
| **線 18 ↔ 線 0（真正的格子）** | **根本沒被試過** |

量一下「交點離橫線自己的線段有多遠」，分得非常開：

| 橫線 | 自身長度 | 超出自身線段 |
|---|---|---|
| 線 0（真的） | 5.92 m | **0.00 m** |
| 線 18（真的） | 3.60 m | **0.00 m** |
| 線 13（假的） | 0.98 m | **2.53 / 6.56 m** |

→ 新增 `CROSS_REACH = 1.2 m`：橫線自己的線段要真的伸到交點附近。
被停著的車擋掉中間一段還是過得了（`pieces` 的首尾涵蓋整段）。

### 2. 地上漆的車位號碼被當成機車格的 T 字

修掉 1 之後格子成形了，換 `interior()` 把它刷掉 —— 而且是「機車格 T 字」那一關：
沿橫邊往格內探，探到細細的、左右 0.2 m 都沒有的短線頭。

那台車前面地上漆著車位號碼 **「565」**。把遮罩的連通元件量出來：

| 元件 | 尺寸 |
|---|---|
| 真的標線 | 2.32 × 5.24 m、1.00 × 5.56 m |
| 干擾物（號碼筆畫） | **0.12 × 0.36 m**、**0.12 × 0.20 m**、0.08 × 0.08 m … |

中間空得很。→ 新增字形遮罩 `GLYPH_M = 0.60 m`：遮罩連通元件**兩個方向都**小於
0.6 m 就是字形（車位號碼、箭頭、補土、油漬），格內檢查時不算命中。
斜紋禁停區的斜線是細長的，不會被誤判成字形，照樣擋得下來。

一定要在**沒膨脹**的脊線上算連通元件 —— 膨脹會把號碼的筆畫和旁邊的標線串成同一個
元件（實測那顆 0.12 × 0.20 的blob 膨脹後併進了 2.44 × 5.36 的大元件，就抓不出來了）。
算完兩邊各自膨脹，只有「附近完全沒有結構標線」的像素才算字形。

### 3. 同一批號碼又灌爆了「格內雜線比例」

修掉 2 之後還是 0 格，這次卡在 `_clutter`（格內雜線比例 > 8 % 就刷掉，本來是用來擋草叢、樹影的）：

```
格 15.1 m²：取樣 1685 點，看得到 67 點（4.0 %），其中遮罩 6 點（9.0 %）—— 6 點全是漆上去的號碼
```

自己停在格子裡的時候，格內九成以上是自車排除區，剩下那一小條剛好有車位號碼，
比例就爆了。→ `_clutter` 也套同一份字形遮罩。

（中間試過「看得到的比例太低就不判斷」，以及「格子大半在俯視圖外就不算」。
前者會讓斜紋禁停區多出誤報；後者量過 TP 與 FP 的分布完全重疊
（TP 中位數 0.59、FP 0.61），分不開，所以兩個都沒有採用。）

## 結果

實車四張原始擷取：

| 擷取 | 修之前 | 修之後 |
|---|---|---|
| `raw_20261103_181414`（地下室） | 0 格 | **1 格** 2.5 × 6.2 m，有車 |
| `raw_20261103_181806`（地下室） | 0 格 | **1 格** 2.5 × 6.2 m，有車 |
| `raw_20261104_121425`（戶外） | 1 格 | 1 格 |
| `raw_20261104_122427`（戶外） | 0 格 | 0 格 |

合成評估（`stats 14`，8 種場景各 14 張）：

| 類型 | 修之前 | 修之後 |
|---|---|---|
| 斜角 a | R 0.525 | **R 0.575** |
| 平行 l | R 0.680 | **R 0.720** |
| 垂直 p | R 0.743 | **R 0.765** |
| 誤報 | 1 | 1 |

對抗場景（`adv 20`，14 種各 20 張）：整體 R 0.569 → **0.585**，P 0.995 → 0.990。
其中**漆字場景 `text` R 0.487 → 0.625**（正是實車遇到的情況），
`seam` 0.639 → 0.656、`occl` 0.391 → 0.406、`stopper` 0.711 → 0.724。

### 代價：斜紋禁停區多兩個誤報

`hatch`（斜紋禁停區）從 0 個誤報變成 2 個（64 張裡，P 1.000 → 0.959）。
原因是舊版擋下斜紋區**靠的就是那些假交叉**：斜線的延長線把禁停區切得稀碎，
湊不出停車格大小的格子。這是碰運氣，不是真的在擋它 —— `CROSS_REACH` 一修，
就得靠 `_clutter` 和 `interior()` 正面擋，而遠處（9 m 外）的斜線在俯視圖上已經糊掉，
雜線比例只有 0.05–0.06，低於 0.08 的門檻。

試過把 `CROSS_REACH` 調緊（0.3 / 0.5）反而更糟（誤報變 4 個）—— 交叉擋得越兇，
禁停區越容易湊出乾淨的大格子。真正要補的是 `interior()` 對斜線的處理，不在這一版的範圍。

**實務影響：可能在斜紋禁停區上畫出一格。** 畫面上看得到斜紋，所以不至於誤導，
但這是已知的退步，記在這裡。

## 回歸測試

`ParkingSlotDetectorTest.realGarageSlotFound` 直接吃使用者那兩張地下室擷取
（`quad_garage1` / `quad_garage2`，從原始四分割畫面拼出 BEV 再存成 fixture），
斷言找得到 2.0–3.2 m × 4.5–7.0 m 的格子且標成有車。
上面三個原因只要回來任何一個，這個測試就會變 0 格。

`matchesPrototype` 也涵蓋這兩張：Kotlin 與 Python 原型逐格比對（角點 0.02 m、信心 0.01）。
重新產生 fixture：

```
AVM_RAW_DIR=~/Downloads/<原始擷取資料夾> python3 tools/parking_proto.py fixtures
```

## 還沒解決的

- **類型判錯**：自己停的那一格被判成「平行」而不是「垂直」。只看得到自己這一格、
  看不到鄰格時，相對自車的幾何本來就一模一樣，尺寸投票也兩邊都符合。位置是對的。
- **空格還沒驗證過**：這四張擷取沒有一張拍到「有畫格線的空停車格」。
  上面修的都是「自己停的那一格」。要驗證空格，需要一張停車場走道、看得到空格線的原始擷取
  （App 控制列的「存原始畫面（校正用）」）。
