# 障礙物偵測（HeightDetector）

柱子、牆、路緣、別人的車身 —— 這些東西 YOLO 不一定認得，但停車時撞到的就是它們。
`HeightDetector` 不靠任何模型，只用「四顆魚眼鏡頭的重疊區」做垂直平面掃描。

## 原理

全景俯視圖是把畫面投影到 **y = 0 的地面平面**拼起來的。對真正貼在地面的東西，
四顆鏡頭投影過去會對得起來；對高出地面的東西（柱子、車身），每顆鏡頭的投影會
往**遠離該鏡頭的方向**拉出一條拖痕，彼此對不起來。

所以：對同一個地面格子，假設一組高度 `h ∈ {0, 0.15, 0.30, 0.50, 0.80}`，
把 (x, h, z) 這個空間點投影回各鏡頭取樣。
- 這個格子真的是地面 → `h = 0` 時各鏡頭取到的顏色最一致
- 這個格子上面有東西 → 某個 `h > 0` 時才一致

把「最佳高度不是 0 的程度」當分數，門檻化之後做形態學 opening、連通元件，
就得到一塊一塊的拖痕。物體本體在拖痕**靠車子的那一端**，所以回報的 `(x, z, w, l)`
取最近的 0.6 m 一帶。

照度／白平衡／暗角四顆鏡頭都不一樣，所以比對前先減掉局部平均（方框半徑 8 格 = 2.72 m）
把偏移吃掉，只留增益要對；紋理太平的地方（`TEX_FLOOR`）直接判定不了，不出分數。

## 管得到哪裡（重要）

**只有兩顆以上鏡頭都看得到的地方算得出來，也就是四個斜角的楔形區。**

| 項目 | 數值 |
|---|---|
| 車身外、≥2 顆鏡頭看得到 | **41.8 %** |
| 再扣掉距離門檻後可判定面積 | **約 65 m²** |
| 距離範圍 | 車身矩形外 0.25 m ～ 4.2 m |
| 偵測高度下限 | 約 10 cm |
| 定位誤差 | 偏**外側** 0.97–1.41 m（合成方柱實測） |

**正前、正後、正左、正右完全是盲區** —— 那裡只有一顆鏡頭。
而停車時最可能撞到的柱子，往往就在正側邊。這是這個方法的結構性限制，
不是調參數能解決的；正側邊要靠 PDC 雷達或原廠超音波。

## 效能

| 畫面 | 桌機中位數 | 推估車機（Mali-G52，× 6–10） |
|---|---|---|
| 960×540 | 2.28 ms | 14–23 ms |
| 1920×1080 | 1.98 ms | 12–20 ms |

跟 YOLO 搶 CPU，所以 `QuadActivity` 只在**車速 < 15 km/h 或車速不明**時跑，
而且**每 4 輪才跑一次**（柱子和牆不會動，更新率低沒關係）。
結果 TTL 4 秒。可以用控制列的「障礙物」按鈕整個關掉。

### 取樣：只轉需要的那些點

1920×1080 全幀轉 ARGB 是 200 萬次色彩轉換，但 `sample()` 實際只讀得到其中約一成。
所以 `HeightDetector.pixelsNeeded(w, h)` 會回報「這張畫面真正會被讀到的像素位置」，
`QuadActivity` 照這份清單填就好。

降解析度到 960×540 也能省同樣的時間，但實測四張實車畫面**會少掉一個真實目標**
（`raw_20261104_121425` 的 (3.60, 5.24) conf 1.00），所以不走那條路。

`pixelsNeeded` 漏掉任何一點，偵測就會讀到沒填過的值、而且不會有任何錯誤訊息，
所以 `HeightDetectorTest.sparseFillMatchesFullFrame` 用「只填清單上的點、其餘填互補垃圾色」
的畫面跑一次，結果必須跟整張都填一模一樣。

## 試過但沒有用：拿障礙物當停車格偵測的車輛框

`ParkingSlotDetector` 有個 `_interior` 檢查：格子**裡面**有線就把這一格刷掉。
停在格子裡的車，它的車身邊緣會被當成「格內有線」，所以整格被刷掉。
傳進去的 `vehicles` 框會把框內像素標成 `state = 2`，`interior()` 就會跳過那些點 ——
所以「把 YOLO 沒抓到的停放車輛補上」理論上應該能救回這些格子。

`HeightDetector` 確實找得到那些停放的車（上表），所以把障礙物矩形當 `vehicles`
餵進去看起來是個自然的修法。**實測四張實車擷取，完全沒有幫助：**

| 畫面 | 無車框 | 障礙物近端當車框 | 障礙物全拖痕當車框 |
|---|---|---|---|
| `raw_20261103_181414` | 0 格 | 0 格 | 0 格 |
| `raw_20261103_181806` | 0 格 | 0 格 | 0 格 |
| `raw_20261104_121425` | 1 格 | 1 格 | **0 格**（變差） |
| `raw_20261104_122427` | 0 格 | 0 格 | 0 格 |

（121425 那一格是自車自己的輪廓，本來就是誤報。）
全拖痕版本還會蓋掉真正的格線，反而更糟。**所以沒有接這條線。**

> **後續（v0.4.5）**：停車格 0 格的真正原因跟障礙物無關，是另外三件事 ——
> 無限長直線算出的假交叉、地上漆的車位號碼被當成機車格 T 字、同一批號碼灌爆格內雜線比例。
> 修好之後兩張地下室擷取都找得到格子了。見 [`parking-slots.md`](parking-slots.md)。

## 顯示

3D 面板畫成半透明量體 + 地面外框 + 距離標籤「障礙物 x.x m」，
距離是到**車身矩形**的距離，不是到原點：

- ≥ 1.2 m：琥珀色
- < 1.2 m：橘色
- < 0.5 m：紅色（標籤同時套 `.danger`）

刻意不畫成有稜有角的實體 —— 這個方法只知道「這裡有東西高過地面」，
不知道是什麼、也量不準，畫得太精確會誤導。
